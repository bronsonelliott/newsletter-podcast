API Weekly

Welcome to this week's API Weekly. Three pieces of news landed right as the year winds down, and they're worth a few minutes before you get to the long read.

Verity cut the price of its API by 40 percent, effective Monday. If you've been putting off a cost review, this is a good excuse to run the numbers again. A cut that size changes which calls are worth making, and it's worth checking whether any workaround you built to save money now costs more in upkeep than it saves. My take: price drops like this are welcome, but they shouldn't make you stop optimizing. Prices move around. Good design holds up regardless.

Northwind released Kestrel-12B, an open model with 12 billion parameters, under the Apache 2.0 license. That license lets companies use it commercially, which matters more to most of us than the benchmark charts. Plenty of teams have wanted a model they can run without an agreement that reads like a novel. Whether Kestrel-12B fits your workload is a question for your own tests, not a launch post. I'd spend an afternoon sending your real prompts through it before deciding anything.

Tessel will launch Tessel Voice, its phone assistant, worldwide on December 8. Voice features tend to generate a lot of short, repeated requests, which is exactly the kind of traffic that rewards caching. If you build for mobile users, keep that in mind as the launch approaches. Your users will also start expecting your app to work well in a voice-first setting, so it's a good time to check how your endpoints handle quick, conversational bursts.

That brings us to the long read. Caching is the cheapest performance win most API developers never fully set up, and this issue walks through it from the ground up.

Start by figuring out what is actually repeated. Pull a day of logs and group your requests by endpoint and parameters. You'll usually find a small set of calls that make up most of your traffic, such as a product catalog lookup, a currency rate, or a user's profile header that every page loads. Those are your candidates. Don't start by caching everything. Caching adds complexity, and complexity spent on rarely repeated requests is wasted effort.

Next, decide what "the same request" means. A cache key is the identity of a response, and it has to include everything that changes the answer: the path, the query parameters you care about, the language header if the response is localized, and the version of your API. Leave out anything that doesn't affect the response, like a random tracking parameter, or you'll store the same answer under a dozen keys and your hit rate will look terrible. Normalize keys before you store them. Sort query parameters, lowercase what should be case-insensitive, and strip the noise.

Then decide how long a response stays fresh. This is the time-to-live, or TTL. A currency rate might be fine for a minute. A product description might be fine for an hour. A list of a company's countries might be fine for a week. The right value depends on how wrong you can afford to be and how often the underlying data changes, so ask the people who own the data rather than guessing. Write the TTL down next to the endpoint so the next developer doesn't have to rediscover it.

Once you know the TTL, tell the outside world about it. HTTP gives you good tools here. A Cache-Control header with a max-age value tells browsers and intermediate proxies how long they can reuse a response without asking you again. For data that changes unpredictably, return an ETag, which is a fingerprint of the response. When a client sends it back in an If-None-Match header, your server can reply with a short not-modified response instead of the full payload. That saves bandwidth on every revalidation even when the data hasn't changed, and it's one of the least-used features in the whole protocol.

For the server side, you'll want a shared cache rather than a per-process one. An in-memory cache inside each worker is fast, but each worker warms up separately, and a deploy throws everything away. A shared store that all your instances read from keeps hits high across the fleet. The trade-off is one more network hop and one more thing that can fail, so have a plan for what your service does when the cache is down. In most cases the right answer is to fall through to the origin and accept the slower path, not to return an error.

One more thing on Verity, because the headline has been going around all day. The fine print on the pricing page says the 40 percent cut covers the batch API only. Prices for regular, real-time calls have not changed.

Be careful about the stampede problem. When a popular entry expires, a flood of requests can arrive at once, all miss the cache, and all hit your backend together. Request coalescing, sometimes called single-flight, fixes this. Only one request goes to the origin for a given key while the others wait for its result. Pair that with stale-while-revalidate behavior, where you serve the slightly old value immediately and refresh it in the background. Users see a fast response, and your database sees one query instead of a thousand.

Invalidation is where most caching bugs live. Expiring by time is simple and forgiving. Expiring by event is more precise but easier to get wrong. If a customer changes their address, you need to clear every cached response that includes it, and a missed key means someone sees stale data for the full TTL. Keep a mapping from entities to the keys that contain them, or use tags if your store supports them, and test invalidation as carefully as you test the happy path. Stale data bugs are quiet. Nobody files a ticket that says "the price is wrong by a little," but they do lose trust in your product.

Know what not to cache. Anything tied to a specific user's authorization should be keyed by that user or left out entirely, because serving one customer's private data to another is the kind of mistake that ends careers. Be cautious with responses that contain personal data, with error responses that might be transient, and with any endpoint where a write and a read need to be consistent. A useful rule: if you can't explain in one sentence why a response is safe to share, don't cache it.

Finally, measure it. Track your hit rate per endpoint, not just overall, because a healthy average can hide one route that never hits at all. Watch latency at the p95 level, since caching usually helps the tail the most. Log misses with their keys occasionally so you can spot keys that never repeat and remove them from the cache path. Revisit your TTLs every few months, because the data behind them changes, and so does the traffic.

Caching done well is mostly boring: a clear key, an honest expiry, a plan for failure, and a dashboard you actually look at. Do the boring parts carefully and the performance gains tend to follow. Next week we'll look at retry strategies, including why your exponential backoff probably needs jitter. Until then, keep your keys normalized and your TTLs written down.

Caching has a second half that most guides skip, and it's the part where I've been burned the most: the cache key is a promise. Every input that changes the response needs to be in the key, and every input that doesn't should stay out. Miss one and you serve the wrong answer to the right person. Include too much and your hit rate quietly drops to nothing while everything looks fine on paper.

Start by writing the key down as a sentence. "This response depends on the resource ID, the locale, and the API version, and nothing else." If you can't finish that sentence without saying "and the user's role, sometimes," you have a problem to solve before you write any code. Our team once spent two days chasing a bug where a translated error message was cached under a key that ignored the Accept-Language header. Nobody had thought of the header as part of the answer, so nobody put it in the key.

Think about where invalidation lives, too. Time-based expiry is the easy default, and for read-heavy catalog data it's often fine. But when a write happens, you should know exactly which keys it touches. Build that mapping when you build the write path, not after the first complaint. A small table in the codebase that says "updating a product invalidates product:{id} and category:{categoryId}" will save you from the 3 a.m. search for the one stale page.

Pick your failure mode on purpose. When the cache is down, do you fall through to the database and accept the extra load, or do you fail the request? For most APIs the answer is fall through, with a circuit breaker so a dead cache doesn't add latency to every call. Write that choice down too, because the first outage is a bad time to decide it.
